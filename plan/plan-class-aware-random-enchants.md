# Plan: plan-class-aware-random-enchants.md

**PRD:** @docs/prd-class-aware-random-enchants.md
**Date:** 2026-09-19


## Context

Модуль `mod-random-enchants` уже пытается фильтровать зачарования по классу, но делает это некорректно: в `modules/mod-random-enchants/src/random_enchants.cpp:180-210` фильтр построен на диапазонах числового `enchantID` (`enchantID < 400`, `>= 200 AND < 500` и т. п.). Идентификатор зачарования не связан с типом характеристики, поэтому фильтр фактически случаен — разбойник получает интеллект, маг получает рейтинг защиты. Гибридные классы (паладин, шаман, друид) не фильтруются вообще (`statFilter = ""`).

Цель: заменить эту эвристику реальной классификацией эффектов зачарования по `SpellItemEnchantment.dbc` и подбирать их по классу, уровню и доминирующей ветке талантов, а также полностью убрать из пула стихийные сопротивления и стихийный урон.

## Existing architecture

- `modules/mod-random-enchants/src/random_enchants.h` — `PlayerScript` с хуками `OnPlayerLootItem`, `OnPlayerCreateItem`, `OnPlayerQuestRewardItem`, `OnPlayerGroupRollRewardItem`. Все хуки передают валидный `Player*` и `Item*`.
- `modules/mod-random-enchants/src/random_enchants.cpp`:
  - `rollPossibleEnchant()` — проверки конфига, выбор до 3 слотов зачарования, ограничение одного слота для `ItemLevel < 15`.
  - `getRandEnchantment()` — расчёт тира по качеству предмета, кап тира по `ItemLevel`, SQL-запрос к `item_enchantment_random_tiers`, затем фильтр кандидатов по величине эффекта (`GetStatCapForItemLevel` / `GetEnchantStatMagnitude`). Эта существующая логика тира и капа остаётся без изменений.
  - Переменная `playerClass` в `rollPossibleEnchant()` объявлена, но не используется.
- Таблица `world.item_enchantment_random_tiers` (`enchantID`, `tier`, `class`, `exclusiveSubClass`), ~700 строк — источник пула. Схема и данные не меняются.
- DBC: `SpellItemEnchantmentEntry` (`src/server/shared/DataStores/DBCStructure.h`) — массивы `type[3]`, `amount[3]`, `spellid[3]`. Для `ITEM_ENCHANTMENT_TYPE_STAT` (5) `spellid[i]` содержит `ItemModType`; для `ITEM_ENCHANTMENT_TYPE_RESISTANCE` (4) — индекс школы (`0` = броня, `1..6` = свет/огонь/природа/лёд/тень/тайная); для `ITEM_ENCHANTMENT_TYPE_DAMAGE` (2) — плоский физический урон оружия; типы `1/3/7` — спелл-проки.
- `ItemModType` (`src/server/game/Entities/Item/ItemTemplate.h`) — полный список статов, по которым строятся профили.
- Определение ветки талантов средствами ядра: `Player::GetTalentMap()`, `Player::GetActiveSpecMask()`, `GetTalentSpellPos()`, `sTalentStore`, `GetTalentTabPages(class)`. Эталон использования — `AiFactory::GetPlayerSpecTabs()` в `modules/mod-playerbots/src/Bot/Factory/AiFactory.cpp`. Реализуем собственную копию логики подсчёта: зависимости `mod-random-enchants` от `mod-playerbots` не вводим, и нужна своя обработка ничьей (у `AiFactory::GetPlayerSpecTab` при равенстве выигрывает первая ветка, PRD требует отката на класс).
- `modules/mod-playerbots/src/Mgr/Item/StatsWeightCalculator` (`CalculateEnchant`) — только справочный ориентир по весам статов для спеков, кодом не используется.
- Тесты: общий таргет `unit_tests` (`src/test/CMakeLists.txt`) на этом чекауте не линкуется (`WorldMock` не реализует `IWorld::AddQueryHolderCallback`) — см. комментарий в `modules/mod-ai-director/mod-ai-director.cmake:9`. Рабочий шаблон — отдельный тестовый исполняемый файл через `<module>.cmake` с `cmake_language(DEFER ...)`, как в `modules/mod-dungeon-clear/mod-dungeon-clear.cmake` и `modules/mod-ai-director/mod-ai-director.cmake`. У `mod-random-enchants` сейчас нет ни `CMakeLists.txt`, ни `.cmake`.

## Решения, принятые с пользователем

- Ветка талантов — строго доминирующая по очкам; ничья или 0 очков → только класс и уровень.
- Набор статов фиксируется в момент ролла, при смене талантов не пересчитывается.
- Уже наложенные зачарования не трогаем, миграции данных нет.
- Стихийный урон и стихийные сопротивления убираются из пула без компенсации.
- Смешанные зачарования фильтруются строго: любой чужой стат → кандидат отбрасывается.
- Броня (`RESISTANCE`, школа 0) остаётся; стихийные проки убираются.
- Таблица «класс + ветка → разрешённые статы» хранится в коде модуля.
- Рейтинги выдаются только начиная с порогового уровня персонажа (по умолчанию 60), настраиваемо.

## Implementation phases

### Phase 1: Реальная классификация зачараний и фильтр по классу

**Goal:** Эвристика по диапазонам `enchantID` удалена. Кандидат принимается только если все его эффекты входят в классовый набор владельца; стихийные сопротивления и стихийный урон не выпадают ни одному классу.

**Touches:**
- module: `modules/mod-random-enchants/src/RE_StatProfile.h/.cpp` (новые, чистая логика), `modules/mod-random-enchants/src/RE_EnchantFilter.h/.cpp` (новые, чтение DBC), `src/random_enchants.cpp`
- build: `modules/mod-random-enchants/mod-random-enchants.cmake` (новый), `modules/mod-random-enchants/tests/StatProfileTest.cpp` (новый)

**Tasks:**
- [ ] В `RE_StatProfile` задать битовую маску групп статов и статические наборы `класс → маска` (объединение трёх веток класса). Правила: чистые физические классы (воин, разбойник, рыцарь смерти) — без `INTELLECT`, `SPIRIT`, `SPELL_POWER`, `MANA`, `MANA_REGENERATION` и спелл-рейтингов; чистые заклинатели (маг, чернокнижник, жрец) — без `AGILITY`, `STRENGTH`, `DEFENSE_SKILL_RATING`, `DODGE/PARRY/BLOCK`, `ATTACK_POWER`, физического урона оружия; охотнику `MANA`/`INTELLECT` разрешены, `SPIRIT`/`SPELL_POWER`/спелл-рейтинги — нет. Функция `IsEnchantAllowed(effects, allowedMask)` — чистая, без `Player` и DBC.
- [ ] В `RE_EnchantFilter` реализовать `DescribeEnchant(enchantId)`: развернуть `SpellItemEnchantmentEntry` в список эффектов; `STAT` → `ItemModType`; `RESISTANCE` школы 0 → броня (разрешена), школ 1..6 → признак «стихийное сопротивление»; `DAMAGE` → физический урон оружия; `COMBAT_SPELL`/`EQUIP_SPELL`/`USE_SPELL` → разбор `SpellInfo` и признак «стихийный урон», если спелл наносит урон конкретной школы или модифицирует урон конкретной школы (не физической).
- [ ] Любой кандидат с признаком «стихийное сопротивление» или «стихийный урон» отбрасывается безусловно, независимо от класса и тира.
- [ ] В `getRandEnchantment()` удалить блок `statFilter` и его SQL-подстановку; SQL-запрос, расчёт тира и кап по `GetStatCapForItemLevel` оставить без изменений. Кандидатов из результата отсеивать новым фильтром, возвращать первый прошедший. Убрать неиспользуемую `playerClass` в `rollPossibleEnchant()`.
- [ ] Добавить `mod-random-enchants.cmake` с отдельным таргетом `mod_random_enchants_tests` (шаблон `mod-dungeon-clear.cmake`) и тесты на `RE_StatProfile`: разбойник отклоняет интеллект/дух/силу заклинаний/ману, маг отклоняет ловкость/силу/рейтинг защиты, смешанный набор «ловкость + интеллект» отклоняется для обоих, стихийное сопротивление и стихийный урон отклоняются для всех классов.

**Verification:**
- build: сборка `worldserver` и `mod_random_enchants_tests` инкрементально, полный лог в файл, проверка первой ошибки
- automated tests: `mod_random_enchants_tests` — все кейсы зелёные; предварительно убедиться, что тесты падают до реализации фильтра
- runtime: на тестовом персонаже-разбойнике и персонаже-маге многократно получить предметы (`.additem` / лут) и проверить наложенные зачарования в тултипе
- DB/log: read-only проверка, что `item_enchantment_random_tiers` не изменилась

**Done when:** Разбойник ни разу не получает интеллект, дух, силу заклинаний и ману; маг ни разу не получает ловкость, силу, рейтинг защиты/блока/парирования; ни один класс не получает стихийное сопротивление или стихийный урон; поведение тиров и частота зачараний не изменились.

### Phase 2: Подбор по доминирующей ветке талантов

**Goal:** Гибридные классы получают статы своей роли; при отсутствии или ничьей очков применяется классовый набор; поведение выключается конфигом.

**Touches:**
- module: `RE_StatProfile.h/.cpp`, `RE_EnchantFilter.h/.cpp` (или новый `RE_SpecResolver.*`), `src/random_enchants.cpp`
- config: `modules/mod-random-enchants/conf/random_enchants.conf.dist`
- runtime: чтение талантов активного спека в момент ролла

**Tasks:**
- [ ] Реализовать `ResolveTalentTab(Player*)`: подсчёт очков по трём веткам активного спека через `GetTalentMap()`, `GetActiveSpecMask()`, `GetTalentSpellPos()`, `sTalentStore`, `GetTalentTabPages()`; возврат «ветка не определена», если сумма очков 0 или максимум делят две и более ветки.
- [ ] Задать наборы статов для 30 связок «класс + ветка» (танк / физический DPS / дальний бой / кастер-DPS / лекарь), классовый набор оставить объединением трёх веток.
- [ ] Прокинуть разрешённую маску в фильтр кандидатов в `getRandEnchantment()`; читать класс, уровень и таланты один раз за ролл, результат не сохранять.
- [ ] Добавить конфиг `RandomEnchants.UseTalentSpec` (по умолчанию `1`); при `0` использовать классовый набор. Существующие ключи и их значения по умолчанию не трогать.
- [ ] Добавить тесты на `ResolveTalentTab`-правила (чистая часть: ничья → не определена, 0 очков → не определена, строгий максимум → ветка) и на наборы веток (друид «Баланс» отклоняет ловкость/силу атаки, друид «Сила зверя» отклоняет интеллект/силу заклинаний).

**Verification:**
- build: сборка `worldserver` и тестового таргета
- automated tests: новые кейсы веток и разрешения ничьей проходят
- runtime: друид с талантами в «Балансе» и второй друид в «Силе зверя» получают предметы — статы соответствуют роли; персонаж с 0 очков и персонаж с ровно равными очками в двух ветках получают классовый набор; при `UseTalentSpec=0` любой спек получает классовый набор
- log: при включённом отладочном логе в логе виден выбранный класс/ветка/уровень для ролла

**Done when:** Ветка талантов наблюдаемо меняет выдаваемые статы; ничья и нулевые таланты дают классовый набор; конфиг-переключатель работает в обе стороны.

### Phase 3: Учёт уровня, пустой пул и диагностика

**Goal:** Рейтинги не выпадают до порогового уровня; при отсутствии подходящих кандидатов зачарование не накладывается вместо выдачи нерелевантного.

**Touches:**
- module: `RE_StatProfile.h/.cpp`, `src/random_enchants.cpp`
- config: `conf/random_enchants.conf.dist`

**Tasks:**
- [ ] Добавить уровневое сужение маски: рейтинги (`DEFENSE_SKILL_RATING`, `DODGE`, `PARRY`, `BLOCK`, `HIT_*`, `CRIT_*`, `HASTE_*`, `EXPERTISE_RATING`, `ARMOR_PENETRATION_RATING`, `RESILIENCE_RATING`, `SPELL_PENETRATION`) разрешать только с уровня персонажа `RandomEnchants.RatingMinLevel` (по умолчанию 60); базовые статы, AP/SP, мана и реген доступны всегда.
- [ ] Добавить ключ `RandomEnchants.RatingMinLevel` в `.conf.dist` с описанием и значением по умолчанию.
- [ ] Если ни один кандидат тира не прошёл фильтр — возвращать «нет зачарования», не откатываясь на нефильтрованный пул; убедиться, что существующая ветка возврата `0` обрабатывается в `rollPossibleEnchant()` так же, как сейчас (слот не заполняется, сообщение в чат не завышает число зачараний).
- [ ] Если класс владельца определить нельзя (нет `Player`, некорректный класс) — зачарование не накладывается.
- [ ] Добавить один лог уровня `DEBUG` на отклонённый ролл с причиной (класс/ветка/уровень/пустой пул); без логирования на каждый кандидат.

**Verification:**
- build: сборка `worldserver`
- automated tests: кейсы «ниже порога рейтинги запрещены», «на пороге разрешены», «пустая маска → нет кандидата»
- runtime: персонаж 20 уровня получает только базовые статы; персонаж 70 уровня получает рейтинги; проверить, что сообщение в чат соответствует фактическому числу наложенных зачараний
- log: в `Server.log` нет спама и нет ошибок на роллах

**Done when:** Пороговый уровень наблюдаемо меняет набор статов; при пустом пуле предмет остаётся без зачарования и сервер не пишет ошибок.

### Phase 4: Кеш классификации и итоговая проверка

**Goal:** Классификация зачарования из DBC выполняется один раз на `enchantID`, полная приёмка по всем критериям PRD пройдена.

**Touches:**
- module: `RE_EnchantFilter.cpp`, `src/random_enchants.cpp`

**Tasks:**
- [ ] Ввести кеш `enchantID → описание эффектов` (заполнение лениво при первом обращении, хранение на время жизни процесса); повторные роллы не перечитывают DBC и `SpellInfo`.
- [ ] Убедиться, что путь ролла не добавил новых обращений к БД: SQL-запрос к `item_enchantment_random_tiers` остаётся один на слот, как и до изменений.
- [ ] Проверить корректность при выходе игрока из игры во время выдачи предмета и при передаче предмета другому классу.
- [ ] Прогнать приёмку по всем критериям PRD, включая PlayerBot заданного класса и ветки.
- [ ] Просмотреть итоговый `git diff` на предмет посторонних изменений.

**Verification:**
- automated tests: полный прогон `mod_random_enchants_tests`
- runtime: по одному персонажу на каждый из 10 классов плюс два гибрида с разными ветками; предмет с уже наложенным старым стихийным зачарованием после перезапуска сервера сохраняет прежние характеристики; предмет, переданный персонажу другого класса, не пересчитывается; `RandomEnchants.Enable=0` — зачарования не накладываются
- log: отсутствие ошибок и предупреждений модуля в `Server.log`
- DB: read-only проверка, что `item_enchantment_random_tiers` и данные предметов не менялись миграциями

**Done when:** Все критерии приёмки PRD подтверждены наблюдаемым поведением, диффе нет посторонних изменений, регрессий в существующем поведении тиров не обнаружено.

## Открытые вопросы

- Требуется отдельное разрешение на запуск/перезапуск тестового worldserver и на GM-команды (`.additem`, выдача талантов) для runtime-проверок фаз 1-4.
- Набор статов для нескольких пограничных веток (усиление шамана, кошка/медведь друида, ретрибуция паладина — доля интеллекта и маны) стоит подтвердить после первой runtime-проверки; стартовые наборы задаются из профилей PRD и при необходимости уточняются в Phase 2.
